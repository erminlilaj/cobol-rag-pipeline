## 0. Read this first — the eight things that will waste your time

1. **The project root is `/Users/Lenovo1/Desktop/desktop/Camera/`** — note the doubled `desktop`.
   An earlier handoff said `/Users/Lenovo1/Desktop/Camera/`; that path exists but is nearly empty.
2. **`docker compose up -d` does nothing when the container is already running.** Source is bind-mounted,
   but Python has already imported it. After *any* source edit you must
   `docker compose restart rag-api` or your change is not live. Several hours were lost to this before.
3. **The chat session is a global singleton** (`_chat_session` in `api.py`, no session id). Your `curl`
   calls and the user's browser share one conversation and one memory. If you test while they use the UI,
   you corrupt their session and they corrupt your measurements. Announce it, or don't test.
4. **Two `ollama serve` processes are bound to port 11434** on this machine (one IPv6 `*:11434` from
   `/usr/local/bin/ollama`, one IPv4 `127.0.0.1:11434` from Ollama.app). They hold **separate model state**.
   Only the IPv6 one is reachable from Docker via `host.docker.internal`. A host-side
   `curl localhost:11434/api/ps` therefore often reports "no models" while a model is loaded. This is a
   **diagnostic trap, not a functional fault** — the container's path is deterministic.
5. **This machine is memory-starved.** Apple M5, 16 GB. Docker Desktop reserves **7.75 GB** for containers
   that use ~0.4 GB. Swap has been observed at 10.5 GB of 11.3 GB used with ~0.1 GB free RAM.
   A multi-minute hang is almost always this, not your code. Check
   `sysctl vm.swapusage` and `lsof -nP -iTCP:11434 -sTCP:LISTEN` before blaming a commit.

6. **`.complete()` is the wrong call for anything a human reads.** LlamaIndex's `Ollama.complete()`
   hits `/api/generate`, which sends the prompt with **no instruct template**. An instruct model then
   *continues* your text instead of answering it. Asked "tu parli bene l'Italiano??" granite replies
   "Bene, tu?" through `/api/generate` at every temperature and under every prompt shape — long preamble,
   chat-shaped prompt, bare question — and answers correctly through `/api/chat`. Structured extraction
   hides this because a JSON schema re-anchors the model, so evidence routing looked fine while small talk
   was gibberish for weeks. **Prose goes through `compose_prose()` in `index.py`; only schema-constrained
   extraction may use `.complete()`.** Related: with this model, *every extra sentence in a system prompt
   costs answer quality*, and an imperative clause comes back echoed verbatim in the reply. Measure prompt
   length the way you measure descriptors.

7. **The corpus registry short-circuits the entity catalogue.** `_catalogue()` in `scope.py` reads
   `corpus.registry.json` first and, when it has `programs`, **returns its entities and never walks the
   artifacts**. The live corpus has that file. So adding an entity source to the artifact-walk fallback in
   the RAG repo changes nothing on a real installation — the entity must be added to
   `_write_corpus_registry` in the **platform** repo, and the registry regenerated. Keep the two in step;
   the fallback still matters for installations without a registry. Regenerating is not part of a normal
   restart: rerun the publish step, or drive `Pipeline._write_corpus_registry` against
   `.runs/_corpus/rag/final_scripts` (it needs Python 3.11+ for `tomllib`, so run it in the container, not
   with the host's 3.9).

8. **The analysis repo is bind-mounted; the platform repo is baked into the image.** A change under
   `control_flow/scripts/` is live in the container immediately. A change under
   `cobol-rag-platform/src/` is **not** — `docker/platform.Dockerfile` does `COPY src ./src` then
   `pip install`, so it needs `docker compose build pipeline`. Consequence, and it has bitten twice:
   **running the pipeline rewrites `corpus.registry.json` with whatever code is in the image**, so a run
   silently reverted the map/mapset entities of `30d4164` and had to be repaired by hand. Worse, it stayed
   invisible afterwards because the API had the catalogue cached (`@lru_cache` on `_catalogue`) — only a
   restart revealed it. **After any pipeline run, check the registry has `map`/`mapset` and regenerate if
   not.** The rebuild is currently blocked: `docker compose build pipeline` fails with
   `DeadlineExceeded` fetching base-image metadata from Docker Hub, which is network, not code.

## 3. Architecture, in the order a question flows

```
question
  → resolve_query_scope (scope.py)        deterministic: program + exact identifiers, session carry-over
  → build_query_plan (query_plan.py)      deterministic skeleton
  → _absent_capability_request (query.py) manifest short-circuit  ← added this session
  → _route_query (query.py)               8B LLM semantic planner → intent, tasks, subtasks
  → _refine_variable_tasks                embedding aspect resolution for variable questions
  → _supplement_missing_capability        additive disagreement veto ← added this session
  → _execute_evidence_subtasks            per-claim execution + reroute ← reworked this session
       → _attempt_evidence_subtask        direct renderer → retrieval → structured → LLM → repair
       → validate_plan_answer             per-claim contracts (query_plan.py)
  → answer
```

Two independent "routers" exist and **they disagree**, which is the single most important thing to
understand about this codebase:

- **The 8B LLM planner** picks `intent` and emits `subtasks`. It is the primary planner.
- **The embedding ranker** (`capability_router.py`) scores the question against 19 natural-language
  capability descriptions using the same embedding model that indexes the corpus.

Historically the ranker was only a *fallback* when the LLM returned nothing. Measurements this session show
the ranker is often right when the LLM is wrong. That gap is where most remaining bugs live.

Thresholds (all calibrated on small samples — **re-measure before trusting on a new corpus**):

| Constant | Value | File:line | Meaning |
|---|---|---|---|
| `MIN_CAPABILITY_SCORE` | 0.55 | capability_router.py | capability match floor |
| `MIN_CAPABILITY_MARGIN` | 0.015 | capability_router.py | lead over runner-up |
| `MIN_ASPECT_SCORE` | 0.45 | capability_router.py:150 | variable-aspect floor |
| `MIN_ASPECT_MARGIN` | 0.05 | capability_router.py:151 | aspect lead |
| `MIN_COMPOUND_ASPECT_SCORE` | 0.55 | capability_router.py:152 | companion aspect floor |
| `MIN_COMPOUND_LEADER_SCORE` | 0.60 | capability_router.py:158 | leader must clear this to admit companions |

## 4. What changed, commit by commit

Seven commits, `77ff7c8..387e432`, **+1621 / −66** across 13 files. Each entry gives the symptom, the root
cause found, and the fix. Read the commit messages too — they carry the reasoning.

### `8cfdd83` — reject evidence that never mentions the entity it claims to describe

**Symptom.** *"Which paragraphs modify NPAGT?"* returned all 32 business rules, **none mentioning NPAGT**,
and validation reported `sufficient`.

**Root cause.** The invariant already existed in `validate_plan_answer` but was gated:
`if plan.intent in {"external_programs", "variable_dataflow"}`. The claim was routed under
`business_rules`, so the check never ran.

**Fix.** Ungated. `NAMED_IDENTIFIER_ENTITY_TYPES` (`query_plan.py:334`) = `{call, variable,
unknown_identifier}`. Matching is a **substring test on purpose**: a group item is satisfied by any
qualified child (`PD1VOCI` ← `PD1VOCI-TABVOX-NUMERO`), while a specific field is *not* satisfied by the
group alone.

Also added `_rerouted_subtask` (`query.py:903`): a claim that fails the entity contract retries against
the best untried capability **that actually indexes that entity type** (`_CAPABILITY_ENTITY_TYPES`), so the
retry is driven by what the evidence layer can hold, not by question wording. Bounded by
`_MAX_CAPABILITY_RETRIES = 2`. An off-entity artifact ends the attempt **before** retrieval or generation
(`reroute_available` flag on `_attempt_evidence_subtask`, `query.py:1017`) — otherwise one bad claim cost
up to 6 model calls. The final attempt still runs the full chain.

### `b87d2b7` — answer from the manifest when a program has no evidence of a kind

**Symptom.** *"Is there any batch JCL associated with PDCBVC?"* returned a program summary.

**Root cause — and it was a bug I introduced in the previous session.** `_rank_question_capabilities`
*removed* unavailable capabilities before ranking, reasoning that a capability with no evidence cannot
answer anything. That is wrong: **absence is a recorded finding**. Filtering `jcl_evidence` out forced the
question onto whatever ranked next.

The analysis already had the answer: `jcl.file_io.json` records `has_jcl_linkage: false`, and
`program.capability_manifest.json` records `jcl_evidence: available=false, count=0,
reason="no program-to-JCL linkage in the parsed job steps"`.

**Fix.** `_absent_capability_request` (`query.py:2018`) consults the **unfiltered** ranking *before* a
capability is chosen. Confident match on a proved-empty capability → return the manifest's own reason.
`absent_capability_answer()` in `final_scripts_answers.py` renders it.

### `e4d7a25` — stop small talk inheriting the last entity discussed

**Symptom.** Typing *"how its going"* returned NPAGT dataflow evidence.

**Root cause.** `_looks_like_followup` matched `"its"` in the anaphora regex → session entity inherited →
plan became `technical / variable_dataflow` at confidence 0.7 → the semantic router fell back to the
deterministic plan, which already said `variable_dataflow`. Entirely deterministic, no LLM involved.

**Fix** (`scope.py:351-363`). A pronoun refers back only when *used* as a reference. Before a present
participle it is the subject of a progressive verb — small talk. `"being"` is excepted (passive auxiliary:
*"where is it being used"* does refer back). Possessives refer back only when qualifying a noun.
Verified 20/20 on small talk vs genuine follow-ups.

**Rejected alternative, recorded so you don't repeat it:** gating entity reuse on the capability ranker.
Measurement killed it — *"And where is it tested?"* ranks 0.551, statistically indistinguishable from
*"how its going"* at 0.535. A pronoun-only question has nothing for an embedding to grip.

### `9c3f1be` — a bare imperative continues the topic, and the whole collection is answered

`"how many variables are in PDCBVC?"` → `168`, then `"list them"` → **a list of 12 copybooks.**

Two definitions of "follow-up". `scope.py` already treated `"list them"` as a continuation; the planner's
`_is_explicit_followup` required a leading wh-word, so a bare imperative never matched. Session intent was

one; that divergence *was* the bug.

A continuation is a situation, not a phrasing: refers backward, names nothing of its own. Naming an
identifier starts a new subject — which is also the guard that stops session state following the user to
another program.

**Inheriting intent alone would have been a quieter wrong answer.** The variable renderer caps a
non-exhaustive list at 25 (`final_scripts_answers.py`), so `"list them"` would print 25 rows under a heading
reading 168. A follow-up to a count is exhaustive by construction and the count contract does not carry
over. An explicitly bounded follow-up (`"a few of them"`) stays bounded.

Measured: 5 continuations inherit + go exhaustive, 6 topic changes do not (including the summary pivot the
probe checks for stale-entity leakage), 8/8 on the named-identifier guard, probe 11/11 on the affected
clusters.
